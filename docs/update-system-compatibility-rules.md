# 升级系统兼容性与发布规则

本文是自动更新、安装器、便携 ZIP、持久更新内核及运行时适配的强制规则。新增升级能力、调整发布格式或修改运行时部署方式时，必须先更新兼容矩阵和回归测试，再发布。本文用于降低升级被阻断的风险；单靠规则文档不能数学意义上保证“绝不出错”，发布门禁和真实包验证是必要条件。

适用范围：Windows x64、同一产品与版本线、当前兼容级别允许的版本切换。未知 CPU 架构、未知 .NET 主版本、跨版本线和低于兼容级别高水位的回退不属于受支持场景。

## 当前实现审查结论

当前升级链路由几部分组成：`UpdateService` 汇总 GitHub、GitCode 和通用清单中的版本并按安装形态选择包；schema 2 更新计划保持旧客户端协议兼容；根目录原生 `update.exe` 选择 `.Updater` 中的持久更新引擎；引擎校验包、运行时、事务并启动目标主程序；安装器 EXE 与便携 ZIP 使用同一发布载荷。

当前已有的保护措施包括：

- 更新包 SHA-256、HTTPS 限制、ZIP 路径穿越检查、清单与格式校验。
- 更新前检查版本线和兼容级别；持久内核保存兼容级别高水位，避免旧主程序绕过回退限制。
- 应用文件采用写前备份和事务回滚；目标主窗口成功启动后才提交。
- `.Updater`、配置、工作区、插件和安装身份受保护；旧包不能覆盖持久更新器。
- 运行时适配在替换应用前预检；框架依赖包可使用私有运行时和原生兼容宿主。
- Release 脚本显式调用旧版启动桥脚本，并同时生成 ZIP 与安装 EXE；manifest 的根 `package` 保留 ZIP，附加格式放在 `packages`，供旧客户端继续读取。

Preview9 类升级故障的关键失效模式是：下载和包校验成功，旧升级器也完成了文件替换，但新目标应用的启动宿主与目标运行时布局不兼容，导致用户看到 .NET 启动错误。故“文件已下载”“安装器已退出”或“更新引擎已复制完文件”均不能作为升级成功标准；必须验证目标程序实际启动并响应。当前实现依赖发布载荷中的相对路径运行时标记和 `.Updater/compat-host.exe`，不能仅依赖新版本升级器运行时才会执行的适配逻辑，因为旧版本升级器不会认识未来的新适配步骤。

本次为静态审查：核对了发布脚本、更新器、安装器、运行时适配代码及现有测试定义，没有在本轮重新构建或运行测试。已发现的发布风险与需补齐的覆盖见“现存缺口”。

## 不可破坏的兼容性规则

### 1. 协议与版本元数据

1. `schemaVersion`、更新计划协议版本、`minimumUpdaterVersion` 与内部更新内核版本是不同概念。升级内核不能因为内部版本号变大，就提高 manifest 的最低协议版本；否则旧版会在下载前拒绝本可兼容的更新。
2. 发布版本、应用内版本、安装包清单版本、ZIP/EXE 文件名及 Release manifest 的版本必须完全一致。Release 构建必须用确定的 build revision，禁止使用随机版本后缀。
3. 更新必须保持相同 `product`、`line` 和 CPU 架构。兼容级别只能在确认数据格式与旧版本兼容策略后调整；一旦升级到更高 epoch，持久状态的高水位不可因回退而降低。
4. 任意版本切换的承诺受兼容级别、版本线、平台和运行时支持范围约束；不得用“任意版本”描述为不受限制的跨代、跨平台回退。
5. 不得手动覆盖或删除 `.Updater` 来“清理旧文件”。旧应用载荷中的更新器文件必须被保护，只有专用、带哈希校验和事务备份的内核升级路径可以替换根原生入口。

### 2. 更新器与应用运行时

1. 新旧应用可在自包含和框架依赖两种运行模式间切换。每个方向都必须有明确的预检、启动方式和故障行为，不允许假设“目标机已经安装 .NET”。
2. 目标为框架依赖部署时，必须满足其 `runtimeconfig.json` 要求的所有框架。先检查随包私有运行时，再验证系统运行时是否兼容；若两者均不满足，必须在替换主应用文件前终止并说明原因。
3. 目标为自包含部署时，必须验证包内运行时闭包完整；不能借用安装目录里残留的旧 `hostfxr`、旧框架目录或全局环境变量。
4. 需要让 Preview7/8/9/10 等旧更新器直接部署的新包，必须在发布载荷中预置旧更新器可用的兼容启动桥：主 EXE、`.Updater/compat-host.exe`、`.Updater/app-runtime.txt`、`.Updater/app-hostfxr.txt`。标记必须是相对安装目录的包内路径，不得写开发机、构建机或用户目录的绝对路径。
5. 兼容桥必须指向与应用目标框架匹配的私有运行时。兼容宿主须受 updater bundle 逐文件哈希保护；运行时标记须受最终发布包 SHA-256 保护，安装 EXE 还须通过其内部文件清单校验。旧更新器不具备新 `RuntimeAdapter` 时，目标应用仍必须能够自行启动。
6. 新增 .NET 主版本、目标框架、RID、原生依赖或宿主行为时，必须先更新运行时缓存构建脚本、兼容桥选择逻辑和真实升级矩阵；未知框架不得静默回退到任意系统运行时或在线临时下载运行时。
7. 所有运行时失败都必须在事务提交前被发现；主程序启动失败必须触发恢复原文件。启动成功需检查进程仍存活、主窗口标题正确且响应，而不仅是 `Process.Start` 返回成功。

### 3. 安装 EXE 与 ZIP 双格式

1. 后续正式 Release 固定同时提供安装 EXE 和便携 ZIP。manifest 根级 `package` 必须继续指向 ZIP，安装 EXE 放入 `packages`，保证旧客户端忽略新字段时仍能升级。
2. 两种包必须来自同一个干净、确定版本的应用载荷；发布前分别验证版本、版本线、兼容级别、主程序、更新内核、运行时桥、内部文件哈希和用户数据排除规则。
3. 已安装形态根据有效 `.Installation/install.json` 记录选择安装 EXE；便携形态选择 ZIP。格式不存在、标记与内容不符或清单摘要冲突时必须明确失败，不能静默下载另一种未知格式。
4. ZIP 必须保持旧更新器可读，安装 EXE 必须能由当前原生安装器正常打开，也必须能被当前更新引擎的 `--update-stage` 协作模式解出载荷。
5. 安装、修复、覆盖更新和卸载不得删除 `config.json`、`utility_settings.json`、`update-sources.json`、`Workspaces`、`Plugins`、安装身份或事务恢复备份。任何新增用户数据目录必须加入保护规则与测试。
6. Release 文件不得包含构建机状态文件、`state.json`、锁文件、事务备份、用户配置、工作区、机密 Key 文件或不应随公开版发布的内部插件。

### 4. 更新事务、持久内核与回退

1. 先校验计划、目标路径、清单、HTTPS/SHA-256、载荷结构、运行时和持久内核，再变更应用文件。只有 `.Updater` 下的隔离缓存/不可变引擎暂存可以作为预检阶段的额外文件写入；不得提前切换活动内核指针。
2. 所有应用文件替换、兼容宿主更换、删除清单执行都必须纳入同一事务。每个文件首次写入前保存唯一原始快照；回滚按逆序执行，并保留无法完成的恢复日志与备份。
3. 用户取消、下载中断、摘要错误、格式错误、运行时缺失、安装器暂存失败、文件占用、目标应用启动失败、内核自检失败和进程异常退出均不得被报告为成功。
4. 持久内核升级必须先独立暂存、逐文件校验和健康检查；新应用成功启动后才激活新内核。必须保留 last-good 内核，当前槽损坏或未就绪时可以回退到已知可用槽。
5. 从新版本回退到旧应用时，只回退应用载荷，不回退持久更新入口、兼容级别高水位或用户数据。随后仍须能用持久更新器升级回较新版本。
6. 所有事务恢复过程必须幂等；在每个关键写入点强制终止进程后，重新运行更新器应能恢复到完整旧版或完整新版，不得留下不可启动的混合目录。

### 5. 多源、清单和发布资产

1. GitHub、GitCode 和通用 manifest 中同版本同格式的资产必须具有一致的 channel、line、compatibilityEpoch、SHA-256 和大小。跨源摘要或元数据不一致时应隔离冲突源并记录诊断，不得合并成一个候选。
2. GitHub/GitCode Release 的下载 URL 必须绑定到清单所在 Release 的同名资产；不能接受另一个 Release 或未经校验的任意下载 URL。
3. 两个来源都发布时，必须上传完全相同的 ZIP、安装 EXE、`update-manifest.json` 和 SHA256SUMS；任何一站资产缺失或摘要不一致都不能标记发布完成。
4. HTTPS 与 SHA-256 提供传输和内容一致性校验，不等同于发行者数字签名。不得在说明中声称当前系统已验证发布者身份。
5. 不得在新旧 Release 上重复或覆盖同一资产名来替换已经公开的包；应递增 build revision，避免用户端缓存、CDN 缓存及多源聚合拿到同版本不同字节。

## 必须通过的验证门禁

每次修改更新系统或生成正式发布包时，至少完成以下检查，并把版本号、包 SHA-256、测试命令和结果记入发布记录：

1. **代码测试**：运行整个 `TerminalSimulation.Tests`，包含版本线/epoch、高水位、双格式选择、包格式识别、桥接路径校验、运行时选择、事务恢复、用户数据保护和安装/卸载测试。不得只跑新增测试或只看编译成功。
2. **真实发布载荷检查**：从 `Scripts/New-Release.ps1` 生成全新目录中的双格式发布包；解析最终 manifest，逐一核对包名、版本、格式、大小和 SHA-256，并确认安装 EXE 与 ZIP 是同版本载荷。
3. **旧更新器向前升级**：使用未修改的真实 Preview10 ZIP 与其随包旧 `update.exe`，通过 `Scripts/Test-Preview10ToPreview11Upgrade.ps1` 升级到本次发布包；检查目标主窗口实际响应、兼容宿主哈希、runtime 标记均为相对路径、COREHOST_TRACE 指向包内私有运行时，且用户工作区哨兵未变。
4. **持久内核往返**：运行 `Scripts/Test-Preview11RoundTrip.ps1` 的完整往返与 `-FaultScenarios`，至少覆盖 Preview11 → Preview9 → Preview11 → Preview8.2 → Preview9 → Preview11，且在系统运行时和强制私有运行时两种路径下验证。检查降级包没有替换持久入口/内核，升级回来后主窗口正常。
5. **包形态和安装状态**：分别验证便携 ZIP、已安装 EXE 更新、主动全新安装、覆盖安装/修复和卸载；应用及设置中的已安装/便携状态判定要与所选包格式一致。
6. **干净系统验证**：在没有安装任何 .NET Desktop Runtime 的 Windows x64 虚拟机上安装并升级；另外验证有不兼容较新 .NET 主版本、但无要求版本的机器。两者都不得出现 .NET 安装提示。开发机本身装有 .NET 不能替代该验证。
7. **故障注入**：至少覆盖错误 SHA、截断包、ZIP 路径穿越、EXE 冒充 ZIP、缺失/越界 runtime 标记、私有运行时缺失或损坏、活动内核损坏、目标应用启动失败、应用文件被占用、取消、以及事务中断后的二次恢复。每例都须检查旧版可启动、用户数据不变、事务状态已清理或仍可恢复。
8. **多源验证**：模拟其中一个更新源慢、超时或只发布 ZIP/EXE 的情况；检查可用源聚合、安装形态选择、源间冲突隔离和手动选择回退都正确。

适用于当前仓库的基本命令：

```powershell
dotnet test TerminalSimulation.Tests/TerminalSimulation.Tests.csproj -c Release -p:IncludeXunjieCloudPlugin=false
pwsh -File Scripts/Test-Preview10ToPreview11Upgrade.ps1 -Preview11Package "artifacts/publish/<version>/<zip-file>"
pwsh -File Scripts/Test-Preview11RoundTrip.ps1 -ElevenPayload "artifacts/.qa/<payload>" -FaultScenarios
pwsh -File Scripts/Test-Preview11RoundTrip.ps1 -ElevenPayload "artifacts/.qa/<payload>" -PrivateRuntimeOnly
```

真实包往返测试需要仓库中列明的历史 Preview 包、Windows x64 环境及项目所需原生工具链。测试条件不满足时必须标记“未验证/阻断发布”，不能把单元测试或本机手动启动等同于完整兼容验收。

## 现存缺口与发布前必须补齐项

静态审查发现当前实现有良好的适配与事务基础，但还存在以下发布防回归缺口：

1. `SetupPackage.ValidateRuntimeBridge` 在两个 runtime 标记都不存在时会接受载荷。`New-Release.ps1` 当前通过 `Prepare-LegacyRuntimeBridge.ps1` 补齐桥接，因此官方主路径具备桥接；但直接调用 `New-UpdatePackage.ps1`、替换发布脚本或漏跑前置步骤仍可能生成不能被旧更新器启动的框架依赖包。正式发布包验证必须明确要求标记存在且可解析，不能把“若存在才校验”当发布门禁。
2. `New-Release.ps1` 当前构建和生成双格式资产，但脚本本身没有执行上述单元测试、真实旧更新器升级、往返故障测试或无 .NET 虚拟机测试。调用脚本成功只代表产物生成成功，不代表发布已验收。
3. 当前存在 Preview10 旧更新器升级 Preview11 的真实包脚本，以及由 Preview11 持久内核执行的 Preview9/Preview8.2 往返脚本；两者不能代替“未经兼容层升级过的原始 Preview7/8/9 更新器直接升级到最新包”的独立实测。若要继续承诺这条直升路径，必须增加对应真实旧包测试；否则发布说明应准确限定支持路径。
4. 当前架构说明已明确尚未完成无 .NET 干净 Windows 虚拟机验收。任何 Preview11 及后续版本不得把“私有运行时单元测试通过”描述成“无 .NET 用户环境验收通过”。
5. 本轮仅做静态审查，没有重新运行构建或自动测试；因此本文不构成当前工作区构建通过的证明。

上述第 1 项应作为发布脚本/验证器的硬性规则落实；第 2–4 项是发布证据缺口，每次发布必须明确记录是否关闭。任何一次失败都应先修复并重跑完整受影响矩阵，不能通过抬高版本号、绕过兼容级别或仅重打 ZIP/EXE 规避。

## 变更规则

修改运行时、安装格式、持久更新入口、plan/manifest schema、兼容级别语义或用户数据保护路径时：

1. 先更新本文中的支持矩阵和风险说明。
2. 先添加能复现失败模式的自动化测试，再改实现。
3. 更新 release notes、升级文档、manifest 示例和发布脚本，保持相同格式与约束。
4. 执行全部受影响的真实包测试，再生成最终发行物；测试包与正式包必须是同一构建产物，不得以另一次“看起来相同”的构建替代。
5. 记录仍未覆盖的旧版本、系统环境和故障类型，避免把有限测试宣传成绝对兼容保证。
